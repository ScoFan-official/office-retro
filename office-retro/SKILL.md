用户要求对一次**办公会话**做复盘。你的产出是 agent **环境**的改进候选：让下一次运行更顺，而不是替用户重做这次工作。

## 步骤

0. **判定运行形态。** 两种形态能承诺的深度不同，先判定再动手：
   - **工作模式（Agent 形态）**：有本地文件系统、技能目录、定时任务工具、子 Agent 轨迹。能读一手材料、能落盘改动、能回读验证。
   - **对话模式（纯对话形态）**：没有文件系统、技能目录或工具，也没有定时任务。只能基于当前对话可见内容复盘，产出候选清单加「用户手动落点」的操作步骤。
   - 判据：有文件/shell/定时任务工具即工作模式；没有就按对话模式处理，并在首次回复用一句话交代深度（例：本次在对话模式，只能给清单和手动步骤，不能直接改文件）。完成标准：形态已判定并已告知用户。

1. **定位会话与一手材料。** 用户未指定会话时默认当前会话。
   - 工作模式：读会话轨迹、工具输出的落盘文件、后台命令索引、任务公告板、子 Agent 的 assignment 与轨迹、交付物、常驻指令与记忆。各产品的具体路径见「环境适配表」对应行与「参考」下的产品注记。
   - 对话模式：只用当前对话里真实出现的内容。用户没贴、你也读不到的，不要补写，也不要声称检索过历史。
   - 每条候选必须指向具体证据（哪条消息、哪个文件、哪次失败）；凭印象写出的候选丢弃。完成标准：每个候选都有可溯源证据。

2. **确认运行环境。** 查「环境适配表」确定当前产品的常驻指令入口、技能目录、记忆、定时任务。表中没有或标「待验证」的，按探测顺序现场确认，并把结果作为适配改进候选（见步骤 5）。
   - 同一产品还有**运行位置**之分（本地电脑 / 云电脑、个人 / 企业空间）：技能、文件、登录态不互通。先确认这次跑在哪一侧，别把另一侧的路径当作现状。
   - 证据不在本侧时（例如在云电脑复盘一次本地会话），明确写出「本侧看不到 X，需要切到 Y 侧再跑」，不要把缺失当成「无」。完成标准：入口与运行位置都确认，或明确记录哪一类在该产品不存在。

3. **逐类目找候选。** 七个类目每个都要过一遍；没有发现的类目写「无」，跳过的类目视为未完成。

- **确定性门禁**：交付物有没有可脚本化的校验？文档发布后回读、表格数字核对、格式校验、发布前预检。先找环境里已有的检查（Skill 内脚本、现成校验命令），已存在但没接上或悄悄失效的检查本身就是发现。机械性问题（固定格式、路径、参数、数字口径）优先建脚本门禁，不写 prose 规则；判断性问题才进常驻指令。一条没有任何门禁的交付链路（如文档发布无回读验证）本身是发现，不是中性默认。_何时用_：agent 犯了脚本能拦住的错，或交付链路无门禁。
- **Skill 覆盖与质量**：重复出现的手工流程是否该固化成 Skill？已有 Skill 是否踩了未记录的坑、命令过时、缺验证步骤？发现即提议 patch。_何时用_：同一流程第二次手工执行，或 Skill 指引与实际环境不符。
- **记忆与常驻指令**：常驻区（AGENTS/MEMORY/偏好指令）是否膨胀、含失效事实、含不改变行为的指令（no-op）？先看该产品的常驻预算（见适配表，如豆包工作的偏好指令上限 10,000 字符），再逐句测试：这句话相对模型默认行为改变了什么？答不出就整句删。常驻只放导航指针和红线，细节下沉到 Skill 或日志。还要查记忆层之间是否互相矛盾（偏好指令说一套、记忆里存着旧口径）。_何时用_：常驻区变大、记忆与当前口径冲突，或 agent 被过时记忆误导。
- **连接器与工具**：鉴权过期、代理断连、工具缺席、token 昂贵的调用。按需加载工具的产品，先确认工具真的被加载过，而不是临场凭印象调用。修复通道、把恢复步骤沉淀进 Skill、或换更省的调用方式。_何时用_：工具调用失败或明显昂贵。
- **定时任务与自动化**：payload 是否自包含（模板全文 + 上下文目录随任务携带）？触发时间与时区是否正确？含人工确认门禁的流程要改写成「发后通知」或拆成两个任务——每次触发是独立会话，无法挂起等待。云端任务不继承本地环境的产品，还要确认 payload 不依赖本地文件与已装技能。_何时用_：任务跑偏、漏发、产物漂移。
- **信息获取**：关键信息当时拿不到？补只读通道、日志落盘、把获取步骤写进相关 Skill。_何时用_：agent 因缺信息而猜测或绕路。
- **导航**：找文件、找入口花了很久？在常驻指令里加一行导航指针，指向权威位置。_何时用_：探索耗时明显。

4. **按严重度排序呈现候选**（阻断 > 重复损耗 > 隐患），每条附证据、建议动作、落点（哪个文件 / 脚本 / 任务 / 设置项）。等用户逐项拍板后才执行改动；未经确认不改既有 Skill 与常量。执行后回读验证，报告实际状态。
   - 对话模式没有落地面：把每条候选改写成用户能直接做的动作（进哪个设置页、粘贴哪段文本、点哪个按钮），并明说「未执行」。完成标准：每个候选都被用户接受或否决；工作模式下被接受的已落地并验证，对话模式下已给出可执行的手动步骤。

5. **自我改进检查。** 本次若运行在非千问办公产品，或发现了新坑：把改进分成两类——**通用能力改进**（类目、步骤、门禁方法，对所有产品生效）与**专属适配改进**（适配表新增/修正一行，只对该产品生效）。向用户提议本 Skill 的修订内容，确认后更新并递增版本号。适配改进涉及本地 / 云两侧时，分别注明哪一侧验过、哪一侧没验。发布到 GitHub 后，其它产品的使用者按同样路线提交改进。完成标准：两类改进各自被提议或明确判定为无。

待验证产品的探测顺序：先读该产品的帮助/设置确定配置根目录，再依次确认四类入口；确认不了就问用户，把猜测写进表里是禁止的。同一产品分形态时拆成两行（豆包 / 豆包工作即如此），不要合成一行含糊描述。验证一行后更新本表并递增版本号。

Qoder 的一手材料与配置面（2026-11-13 本机验证）：

- 会话记录在 `~/.qoder-cn/projects/<工作区slug>/<sessionId>.jsonl`（Claude Code 兼容格式）；子代理转录在同名目录 `subagents/agent-*.jsonl`。slug 是工作区绝对路径把分隔符与非 ASCII 字符换成 `-`，按它定位当前会话。
- `~/.qoder-cn/settings.json`：`hooks` 走 Claude Code 契约（SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / Stop 等，stdin JSON），确定性门禁可落成 hook 脚本；MCP 连接器在同文件 `mcpServers`。
- 定时任务用内置 `qoder_cron` 工具。cloud 任务不继承本地工作区、工具与插件；本地任务的模型在创建时固化，不随后续会话变化。
- 国际版根目录 `~/.qoder`（AGENTS.md、skills/、settings.json 已确认存在），自动记忆与会话记录未验证。

豆包 / 豆包工作的一手材料与配置面（2026-11-13 本机验证，macOS 客户端 2.36.6）：

- 工作区根：`~/Library/Application Support/Doubao/Default/.doubao/agent_mode/workspace/`。技能发现根目录含 `.skills/`（44 个内置技能，由应用维护）与 `.user_skills/`（自定义投放位，本机为空）；`~/Doubao/skills`、`~/.agents/skills` 同被声明为发现根，但本机未出现在已加载清单，别默认它们生效。
- 会话轨迹：`.sessions/<sessionId>/agents/<agentId>/system/trajectory.jsonl`（逐行 role / content / tool_calls）；单次工具大输出溢出到同目录 `tool-results/<tool>_<sha12>.txt`。
- 后台命令：`conversation/<sessionId>/background_history_task/index.json` 记 command、exitCode、输出文件；正文在 `outputs/*.output`。
- 多 Agent：`.sessions/<sessionId>/board.md`（任务公告板，含任务 ID / Organizer / 状态）、`agents/<agentId>/system/assignment.md`、`socket/briefing.md`、`socket/findings.jsonl`。
- 跨形态读取：工作模式下 `im_list_conversations` 能列出具对话模式的豆包会话（已验证），正文走同族 `im_get_conversation_messages` / `im_search_message`。
- 无 hooks 配置面：客户端未提供 Claude Code 式 hooks（本机未发现 hooks 配置文件），确定性门禁只能落成 Skill 内脚本、交付后回读、或定时任务；本地电脑的「按需确认 / 始终询问 / 全部允许」只是粗粒度闸门，不能替代脚本校验。
- front matter 只吃 `name` / `description` / `version` / `metadata`（内置技能用 `metadata.requires.bins`、`metadata.cliHelp` 声明依赖与 CLI 帮助）。内置 44 个技能无一使用 `disable-model-invocation`，即该字段在豆包工作不保证生效——「仅用户主动触发」要靠 description 措辞保证。

安装方式、记忆分层、定时任务口径、运行位置差异与对话模式的具体做法见 `references/doubao.md`。

### 执行与复盘的分工

执行会话的 agent 上下文压力最大：探索、产出、排错都在它身上。复盘者拿到的是记录和交付物，无需重新探索，上下文压力最小。所以判断性规则由复盘侧核对与沉淀，执行侧只保留导航指针和红线——往执行侧常驻文件里塞规则，挤占的是干活的上下文。

### 落点选择

- 常驻区（AGENTS/MEMORY/偏好指令）：只放导航指针与红线，每一行都在花常驻上下文和字符上限。
- Skill：流程性知识与用户主动调用的命令；description 常驻，正文按需加载，措辞按 writing-for-agents（若该产品装有此 Skill 先读它）。
- 脚本：机械性校验一律落成脚本，挂进 Skill 或任务，可重复执行。
- 先找已有文档与 Skill 再新建，同一含义只留一个权威位置。

### 发布与贡献

本 Skill 以 GitHub 仓库（ScoFan-official/office-retro）分发，仓库含 SKILL.md、references/ 与 README.md。安装：把技能目录复制到目标产品的技能目录，或在有技能商店/上传入口的产品里直接上传（见适配表）。贡献：在目标产品里跑一次复盘，按步骤 5 产出通用或适配改进，经使用者确认后提交。
