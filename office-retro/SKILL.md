用户要求对一次**办公会话**做复盘。你的产出是 agent **环境**的改进候选：让下一次运行更顺，而不是替用户重做这次工作。

## 步骤

1. 定位会话与产品。用户未指定会话时默认当前会话。读一手材料：会话记录、任务运行日志、交付物文件、记忆与意识文件。每条候选必须指向具体证据（哪条消息、哪个文件、哪次失败）；凭印象写出的候选丢弃。完成标准：每个候选都有可溯源证据。

2. 确认运行环境。查「环境适配表」确定当前产品的意识文件、技能目录、记忆、定时任务入口。表中没有或标注待验证的产品，按表中探测顺序现场确认，并把验证结果作为适配改进候选（见步骤 5）。完成标准：四类入口路径全部确认，或明确记录哪一类在该产品不存在。

3. 逐类目找候选。七个类目每个都要过一遍；没有发现的类目写「无」，跳过的类目视为未完成。

- **确定性门禁**：交付物有没有可脚本化的校验？文档发布后回读、表格数字核对、格式校验、发布前预检。先找环境里已有的检查（Skill 内脚本、现成校验命令），已存在但没接上或悄悄失效的检查本身就是发现。机械性问题（固定格式、路径、参数、数字口径）优先建脚本门禁，不写 prose 规则；判断性问题才进意识文件。一条没有任何门禁的交付链路（如文档发布无回读验证）本身是发现，不是中性默认。_何时用_：agent 犯了脚本能拦住的错，或交付链路无门禁。
- **Skill 覆盖与质量**：重复出现的手工流程是否该固化成 Skill？已有 Skill 是否踩了未记录的坑、命令过时、缺验证步骤？发现即提议 patch。_何时用_：同一流程第二次手工执行，或 Skill 指引与实际环境不符。
- **记忆与意识文件**：MEMORY/USER/AGENTS 类文件是否膨胀、含失效事实、含不改变行为的指令（no-op）？逐句测试：这句话相对模型默认行为改变了什么？答不出就整句删。常驻文件只放导航指针和红线，细节下沉到 Skill 或日志。_何时用_：常驻文件变大，或 agent 被过时记忆误导。
- **连接器与工具**：鉴权过期、代理断连、工具缺席、token 昂贵的调用。修复通道、把恢复步骤沉淀进 Skill、或换更省的调用方式。_何时用_：工具调用失败或明显昂贵。
- **定时任务与自动化**：payload 是否自包含（模板全文 + 上下文目录随任务携带）？触发时间与时区是否正确？含人工确认门禁的流程要改写成「发后通知」或拆成两个任务——每次触发是独立会话，无法挂起等待。_何时用_：任务跑偏、漏发、产物漂移。
- **信息获取**：关键信息当时拿不到？补只读通道、日志落盘、把获取步骤写进相关 Skill。_何时用_：agent 因缺信息而猜测或绕路。
- **导航**：找文件、找入口花了很久？在意识文件里加一行导航指针，指向权威位置。_何时用_：探索耗时明显。

4. 按严重度排序呈现候选（阻断 > 重复损耗 > 隐患），每条附证据、建议动作、落点（哪个文件/脚本/任务）。等用户逐项拍板后才执行改动；未经确认不改既有 Skill 与常量。执行后回读验证，报告实际状态。完成标准：每个候选都被用户接受或否决，被接受的都已落地并验证。

5. 自我改进检查。本次若运行在非千问办公产品，或发现了新坑：把改进分成两类——**通用能力改进**（类目、步骤、门禁方法，对所有产品生效）与**专属适配改进**（适配表新增/修正一行，只对该产品生效）。向用户提议本 Skill 的修订内容，确认后更新并递增版本号。发布到 GitHub 后，其它产品的使用者按同样路线提交改进。完成标准：两类改进各自被提议或明确判定为无。

### 执行与复盘的分工

执行会话的 agent 上下文压力最大：探索、产出、排错都在它身上。复盘者拿到的是记录和交付物，无需重新探索，上下文压力最小。所以判断性规则由复盘侧核对与沉淀，执行侧只保留导航指针和红线——往执行侧常驻文件里塞规则，挤占的是干活的上下文。

### 落点选择

- 意识文件（AGENTS/MEMORY 类）：只放导航指针与红线，每一行都在花常驻上下文。
- Skill：流程性知识与用户主动调用的命令；description 常驻，正文按需加载，措辞按 writing-for-agents（若该产品装有此 Skill 先读它）。
- 脚本：机械性校验一律落成脚本，挂进 Skill 或任务，可重复执行。
- 先找已有文档与 Skill 再新建，同一含义只留一个权威位置。
